# Evidence-backed skill improvement for software teams

Use this for a skill-maintenance candidate inside a bounded improvement pass. It is
a local procedure, not an installed background learner or permission to start a
recurring run. One-off skill authoring remains the job of `loop-skill`.

## Start from observed friction

Collect the correction or reproducible failure and the relevant skill/repository
revision. Separate observed behavior, reported history, hypothesis, and proposed
change. A recurring unnecessary read, misroute, lost handoff constraint, or failed
reproduction can justify a candidate; an agent's self-rating alone cannot.

Prefer a narrow correction, selective reference loading, or a deterministic helper
before increasing prompts or adding ML. An optional local classifier is an advisory
candidate, evaluated against the same routing and acceptance baseline. It does not
replace canonical model routing or change execution authority.

## Candidate lifecycle

| State | Evidence and action |
|---|---|
| **Proposed** | Record the trigger, source/event date, check date, scope, baseline, hypothesis and expected benefit. Keep speculative candidates outside active skill discovery. |
| **Trial** | Preserve the prior version; make a reversible local patch in the authorized scope. Freeze evaluation inputs and acceptance criteria before comparing it with the baseline. |
| **Active** | Promote only the supported instruction or claim after required structural checks and representative behavior evaluation. Record remaining untested paths and the owner who accepted promotion under existing authority. |
| **Stale** | Mark affected claims when a prerequisite/version changes, counter-evidence arrives, or a correction invalidates them. Recheck or restore the prior version; retain provenance. |
| **Archived** | Retain the reason and replacement pointer when deliberately retiring a candidate. This state does not authorize deletion. |

A skill may be active while one proposed optimization remains unverified. A
proposal-only task stays proposal-only; evidence does not expand permission.

## Trial without moving the goalposts

Use realistic software tasks from the intended team: a bounded bug fix, feature
change, review, documentation update, or context handoff as appropriate to the
candidate. Keep the evaluator, task inputs, acceptance criteria, and required checks
versioned and fixed. The agent editing the skill must not weaken them to make its
candidate pass.

When behavioral evaluation is warranted and authorized, give an independent
evaluator the request, candidate skill and minimum raw artifacts. Do not prime it
with the desired answer or the author's suspected fix. Keep a frozen final holdout
outside the improvement agent's readable inputs; an agent exposed to the held-out
tasks is not an independent final evaluation. Visible examples remain useful
development tests, labeled as such. A published toy classifier fixture is likewise
a regression/demo set, not proof of general routing quality.

Choose checks proportional to the change. Reference validation establishes path
integrity; a replay or forward test exercises behavior; acceptance evidence measures
the resulting work. Do not infer the latter from the former. Use the existing
verifier-integrity and held-out-evaluation references when operating the full loop;
this local procedure does not claim their mechanisms were installed or run.

## Record the outcome and stop

Keep a compact record of baseline/candidate revisions, evaluation version, actual
commands and outcomes, acceptance failures, reviewer corrections, retries, latency,
and runtime-reported token/cache usage when available. File bytes or estimated
prompt tokens are static size proxies, **not billed-token savings**. Changed skill
text is **not proven delivery improvement**. Missing usage remains unknown.

Promote only a measured benefit with acceptable quality under the frozen criteria;
otherwise leave the candidate proposed, revise it against development evidence, or
restore the prior version. Stop the pass at its task/budget limit or when there is
no new evidence. Repeatedly rerunning the same failed approach without changed
conditions is not improvement.

End with what changed, evidence, uncertainty, the active/stale claims, and the next
retrieval/rollback pointer. Local edits, model training, remote proposals, paid calls,
publishing, messaging and scheduled work each remain subject to the user's existing
scope; this procedure grants none of them by itself.
