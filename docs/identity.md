# Proof identity

Proof helps people turn a software goal into a bounded artifact and inspectable
evidence. The identity should communicate careful engineering and useful work.
The name is not a guarantee of correctness or a claim of autonomous delivery.

## Names and words

- Product: **Proof**.
- Skill names: `proof-<role>`, with no old-name aliases.
- Banner line: **A skill framework for building better software.**
- Explain the useful result before discussing model tiers or orchestration.
  Avoid claiming that a green local check establishes real-world quality,
  token savings, installed-host support or marketplace approval.

## Visual vocabulary

The established identity uses charcoal, warm ivory, restrained teal, technical
spacing and precise modular forms. Modules, reference cards, an inspection
aperture and an evidence folio are illustration vocabulary; they are not literal
runtime components. Avoid robots, brains, dense neon networks and decorative
status badges that imply measured success.

The native documentation SVGs use these editable tokens:

| Role | Dark | Light |
| --- | --- | --- |
| Canvas | `#101c28` | `#f7fafc` |
| Card | `#172b3b` | `#ffffff` |
| Main type | `#edf7fa` | `#102838` |
| Secondary type | `#aec4d0` | `#4c6373` |
| Accent | `#65e2d2` | `#007c83` |

Use readable sans-serif headings and body copy, with code identifiers kept exact.
Detailed diagrams may retain semantic warning/policy colors; every relationship
must remain understandable without color alone.
